## What you'll build

You'll use Keploy's **Mux + MySQL** sample, a tiny URL shortener written with [gorilla/mux](https://github.com/gorilla/mux). It has three endpoints:

| Endpoint | What it does | Touches MySQL? |
| --- | --- | --- |
| `POST /create` | Stores a link and returns a short URL like `/links/1` | `INSERT` |
| `GET /links/{id}` | Redirects (HTTP 307) to the stored link | `SELECT … WHERE id=` |
| `GET /all` | Lists every stored link as JSON | `SELECT *` |

By the end you will have:

- 4 test cases and 7 MySQL mocks that Keploy generated from real traffic
- a passing test run with MySQL stopped
- a failing test run that catches a change you made on purpose

Plan on about 15 minutes if Go and Docker are already installed.

## What is Keploy?

Keploy is an open-source testing tool that **records** the traffic going in and out of your application and saves it as YAML: the incoming API calls become test cases, and the outgoing calls (here, MySQL queries) become mocks. Later, in **test** mode, Keploy starts your app again, replays the recorded requests, answers the app's database calls from the mocks, and compares each response with what it recorded.

It does this from outside your process. You don't add an SDK or change a line of Go. On Linux, Keploy uses eBPF to route the app's network traffic through its own proxy, so you just wrap your normal start command: `keploy record -c "./main"`.

### Why a Go developer would care

- **No hand-written fixtures.** You don't write `httptest` request tables or `sqlmock` expectations for these flows. They come from real requests.
- **No database needed to run the tests.** Replay uses the recorded mocks. In Step 5 the tests pass while MySQL isn't running at all.
- **Failures are easy to read.** A failed test prints the expected and actual response side by side, and `keploy test` exits with a non-zero code you can gate CI on.

<Callout type="info" title="Two builds of the Keploy CLI">
Keploy's install script can install either an **open-source build** (pass `--oss`) or, by default, an **account-based build** from keploy.io that asks you to run `keploy login`. When it installs the open-source build, the installer prints that this build supports **HTTP and MySQL**, and that PostgreSQL, MongoDB, gRPC, Kafka and native macOS/Windows recording need the account-based build. I ran everything here with the **open-source build, v3.6.87**. That's one reason this tutorial uses the MySQL sample.
</Callout>

## Prerequisites

- **Linux** with kernel 5.10 or newer (Keploy's install docs list this requirement). I used Ubuntu 24.04. Keploy's docs say WSL works too, but I didn't test it.
- **Go**. The sample's `go.mod` says `go 1.21.3`. I built it with Go 1.24.7.
- **A MySQL server** on `localhost:3306`. The official quickstart uses Docker for this.
- **sudo access**, because Keploy's eBPF hooks need root.
- **git** and **curl**.

Start the app on its own first. If something is wrong with Go or MySQL, you'll want to find out now, not in the middle of a recording.

```bash title="Terminal"
go mod download
```

This is the command from the official quickstart. It starts MySQL in Docker with the root password the sample expects:


## Step 3: Record test cases

Now run the same binary under Keploy. Keep MySQL running, because in record mode the app talks to the real database and Keploy writes down what it sees.

<Steps>
<Step title="Start Keploy in record mode">

```bash title="Terminal 1"
sudo -E PATH=$PATH keploy record -c "./main"
```

Here's what each part does:

- `-c "./main"` is the command Keploy uses to start your app. Keploy launches the app itself, so don't start `./main` separately.
- `sudo` is needed because Keploy loads eBPF programs into the kernel.
- `-E` keeps your environment variables. **Without it, `sudo` drops `ConnectionString` and the app exits on startup** (see [Troubleshooting](#troubleshooting)).
- `PATH=$PATH` hands your `PATH` to Keploy and to the app it starts. Even with `-E`, `sudo` on Ubuntu replaces `PATH` with its own `secure_path`, so anything your start command needs from your `PATH` would otherwise go missing. (It doesn't change where `sudo` looks for `keploy` itself. The installer put it in `/usr/local/bin`, which `sudo` already searches.)

### The mocks

`mocks.yaml` holds every exchange between the app and MySQL, decoded at the MySQL protocol level, not saved as raw bytes. Here's the full list from my run:

| Mock | MySQL operation | What it is |
| --- | --- | --- |
| `mock-0` | `HandshakeV10` (type `config`) | The app logging in as `root` |
| `mock-1` | `COM_PING` | `store.Ping()` on startup |
| `mock-2` | `COM_QUERY` | `create table if not exists list(…)` |
| `mock-3` | `COM_QUERY` → `OK` | `insert into list (website) values("https://google.com")` |
| `mock-4` | `COM_QUERY` → `TextResultSet` | `select website from list where id=1` |
| `mock-5` | `COM_QUERY` → `OK` | `insert into list (website) values("https://github.com")` |
| `mock-6` | `COM_QUERY` → `TextResultSet` | `select * from list` |

For example, `mock-3` stores the exact query and the `OK` packet MySQL sent back, including `last_insert_id: 1`. That's where the `/links/1` in the response comes from:

```yaml title="keploy/test-set-0/mocks.yaml (mock-3, excerpt)"

        - header:
            header:
                payload_length: 56
                sequence_id: 0
            packet_type: COM_QUERY

            command: 3

            header:
                payload_length: 7

            header: 0

```

Test cases and mocks are plain YAML, so you can review them in a pull request and edit them by hand. When `keploy test` first runs, it also creates `keploy/.gitignore`, which contains `/reports/`: test reports stay out of git, while the tests and mocks go in.
</Callout>

## What just happened?

Here's how the two modes fit together, based on what Keploy logged during my run:

<RecordReplayDiagram />

- **Recording.** Keploy started its own proxy (`Proxy started at port:16789`), took over DNS resolution for the app, and forwarded the app's port 8080 through itself (`Started ingress forwarding`). Requests from `curl` passed through Keploy on the way in, and the app's MySQL traffic passed through it on the way out. Each incoming request became a test case and each query became a mock, both stamped with request and response timestamps. Keploy uses those timestamps to tie mocks to the test that triggered them: its replay log mentions a "mock window" per test, and the first test run saved the result as `keploy/test-set-0/mappings.yaml`. In my run, that file maps `get-all-1` to `mock-6` (the `select * from list` query) and `get-links-by-id-1` to `mock-4`.
- **Testing.** Keploy restarted the app, saw from the recorded mocks that port 3306 speaks MySQL (`recovered MySQL ports from recorded mocks`), and sent every recorded request again. When the app queried the database, Keploy matched the query against `mocks.yaml` and returned the recorded response. Then it compared the app's HTTP response with the recorded one, skipping the fields marked as noise.

So a Keploy test checks your **Go code's behaviour**, from HTTP handling and JSON encoding to how it uses query results, without needing the database to be there.

### Recording again creates a new test set

Each recording session gets its own folder. When I recorded a second time (a single `GET /all`), Keploy created `keploy/test-set-1`, and the next `keploy test` replayed **both** sets:

<Output label="Output (excerpt)" result="pass">

```text
	Total tests: 5
	Total test passed: 5
	Total test failed: 0
	Total time taken: "20.04 s"
```


## Troubleshooting

These are the problems I actually hit, or deliberately reproduced, while writing this guide.

### "Connection string empty" right after `keploy record` starts

<Output label="Output (excerpt)" result="error">

```text
2026/10/03 15:07:31 Connection string empty
🐰 Keploy: 2026-10-03T09:37:31.253812273Z 	ERROR	error while running the app	{"error": "exit status 1"}
🐰 Keploy: 2026-10-03T09:37:31.253869415Z 	ERROR	user application terminated unexpectedly hence stopping keploy, please check application logs if this behaviour is not expected
```

</Output>

This is what happens if you run `sudo keploy record -c "./main"` without `-E`. `sudo` resets the environment, so the app never sees `ConnectionString`. Use `sudo -E PATH=$PATH …`, and check that you ran `export ConnectionString=…` in the same terminal.

### "connection refused" on port 3306 while recording

<Output label="Output (excerpt)" result="error">

```text
Could not create store dial tcp 127.0.0.1:3306: connect: connection refused
```

</Output>

The app couldn't reach MySQL, so it exited before serving any requests. Recording needs the real database running. (Testing doesn't, because the mocks stand in for it.) Start MySQL again and wait until it accepts connections.

### "Keploy has taken control of the DNS resolution mechanism"

This line appears on every run. It's an informational message, not an error. It just means the app's DNS lookups go through Keploy while it runs.

### A Go sample using PostgreSQL doesn't replay

The open-source build doesn't include a PostgreSQL parser. In its source, the only protocol parsers registered under `pkg/agent/proxy/integrations` are `http`, `mysql` and `generic`, a protocol-agnostic fallback that pairs raw chunks of traffic. For the Postgres-based Go quickstarts (Echo, Mux + Postgres, FastHttp), use the account-based Keploy build from keploy.io. I didn't test that build.

### `go mod download` or `docker run` fails behind a restrictive network

In my sandbox, `proxy.golang.org` and Docker Hub were both blocked. `GOPROXY=direct go mod download` fetched the modules straight from GitHub instead. For MySQL, I used a locally installed server, as described in Step 2. On a normal network you shouldn't need either workaround.

## Wrapping up

You took a Go API you'd never seen, recorded four real requests, and ended up with a test suite that:

- runs without a database,
- passes when nothing changed,
- fails, with a readable diff and a non-zero exit code, when behaviour changes.

You wrote no test code to get there. The `keploy/` folder is plain YAML that sits next to your code, so the natural next step is to commit it and run `keploy test` in CI.
